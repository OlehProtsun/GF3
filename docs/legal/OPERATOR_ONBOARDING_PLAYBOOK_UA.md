# GF3 — практична інструкція для оператора

**DRAFT — робоча інструкція для людської юридичної, фінансової та технічної перевірки.**
Версія: 0.1.0-draft. Підготовлено: 2026-10-08, Польща.
Основа опису застосунку: DEV2, `37540cfffb9fd89bd2a22a54c00cf3f451ce58a3`.
Цей файл не затверджує договори, безпеку сервера чи комерційний запуск.
Заповнені картки, персональні дані, секрети, підписані PDF і докази зберігаються поза Git та публічним хостингом у захищеному сховищі.

## 1. Мета і ролі

Оператор GF3 надає компанії інструмент для графіків, доступності, замін змін і повідомлень. Компанія-роботодавець визначає робочі процеси, уповноважує менеджерів і відповідає за законність графіків та обробки кадрових даних.

Для даних персоналу компанія зазвичай є адміністратором даних, оператор — процесором за її документованими інструкціями. Для власних продажів, рахунків і ділового зв'язку оператор може бути окремим адміністратором. Польський юрист із приватності має перевірити ці ролі за фактичними цілями, одержувачами та підставами обробки; назва ролі в застосунку цього не визначає.

Менеджер керує користувачами й графіками, але може підписувати за компанію лише за підтверджених повноважень. Працівник користується своїм акаунтом, не купує підписку оператора і не підписує SaaS або DPA. Особисте підтвердження правил не замінює трудових документів чи інформації GDPR/RODO.

До DPA і захищеного способу передачі не збирай реальні списки працівників. Не вимагай підпису DRAFT; не обіцяй payroll, автоматичну трудову відповідність, 24/7, 99,9%, ISO/SOC2 чи неперевірене SLA. Після зустрічі заповнюй лише приватну копію картки, уточнюй оферту та передавай питання спеціалістам.

## 5. Підписи і фінальні умови

1. Перевір свою правдиву юридичну особу/ПІБ, адресу, ідентифікатори та законну форму постійного SaaS. Не припускай автоматично зареєстровану компанію або допустимість działalność nierejestrowana. Юрист/бухгалтер перевіряють VAT, ZUS, податки, бухгалтерський документ і KSeF за конкретними обставинами; сама назва B2B нічого не підтверджує.
2. Звір реквізити клієнта та повноваження підписанта. Погодь один комерційний договір на основі довгого SaaS, його scope, домен/функції/кількість користувачів, старт, ціну/валюту/податковий опис, оплату наперед чи після, строк платежу, припинення, експорт і видалення. **500 PLN/місяць, сім днів оплати та інші умови чернетки — приклади, не підтверджена угода.**
3. Коротке замовлення допустиме лише після юридичного узгодження, із явним посиланням на фінальний основний договір. Якщо SaaS уже містить усі умови, не додавай суперечливий другий договір.
4. Погодь DPA: компанія-адміністратор, оператор-процесор; категорії осіб/полів, цілі, строк, інструкції, менеджери, регіон, субпроцесори/transfer, інциденти, запити людей, аудит, повернення/видалення. TOMs описують реально наявний захист і докази. SLA та межі відповідальності — лише погоджені й виконувані, перевірені юристом.
5. Польський юрист і фінансовий радник перевіряють точні фінальні версії. Оператор надає фінальні публічні умови до договору. Після review уповноважені сторони підписують SaaS + scope і DPA/TOMs; SLA лише якщо погоджено. Архівуй версії, підписи, повноваження, дати та докази електронної доставки поза Git/public.

**Приклад ролей без вигаданих осіб:** уповноважений оператор і представник компанії підписують SaaS/scope та DPA/TOMs; менеджер без довіреності цього не робить. Роботодавець доставляє працівникові свою GDPR-інформацію. Працівник у GF3 підтверджує лише свою придатну версію правил застосунку.

Для друку: відредагувати Markdown договору, виконати наявний `node generate-html.mjs` у `docs/legal/saas-agreement`, звірити HTML із джерелом, Chrome/Edge → Ctrl+P → A4 → Save as PDF → переглянути всі сторінки. Генератор і друк не підписують та не затверджують текст.

## 6. Технічне введення клієнта

Це людський runbook, а не виконане в цьому плані розгортання.

1. Технічний власник закриває security gate: PIN/auth/token, обмеження спроб, HTTPS, доступи, моніторинг, backup/restore, storage/cookies, підрядники. Ризики шестизначних паролів і JWT у localStorage залишаються в STOP-SHIP до окремої перевірки/усунення.
2. Один незалежний роботодавець → окрема інстанція, домен, база/volume, конфігурація, секрети та копії. Перевірити ізоляцію даних і доступів на реальному сервері; не змішувати незалежні компанії в одній SQLite. Зробити backup до операцій із даними, перевірити restore на окремому тестовому середовищі. Не видаляти чинний volume і не змінювати його прив'язку навмання.
3. Створити уповноважений manager, локації й мінімальні акаунти. Початковий доступ передати захищено; секрети не записувати в картку. Перевірити відкликання доступу без самовільної втрати кадрової історії. Самореєстрація незалежних фірм не підтверджена.
4. Оператор/юрист звіряють публічні `/legal/regulamin.html` та `/legal/zasady-korzystania.html` з окремим PDF правил застосунку. Визначити назву, дату, версію, SHA-256 і ролі; зберегти реальний review. Відповідальний system manager завантажує/публікує лише затверджений PDF у правильній інстанції. HTML і PDF не синхронізуються автоматично.
5. На свіжих синтетичних manager/employee перевірити: кожна роль бачить тільки належні pending-документи; PDF завантажується; checkbox спочатку порожній; звичайний API до accept → **HTTP 428**; після accept усіх pending → доступ. Auth і дозволені маршрути regulations мають винятки. Нова обов'язкова версія знову блокує, старі записи/PDF зберігаються за погодженою політикою.
6. Перевірити `GET /api/regulations/pending`, `GET /api/regulations/history/me`, `GET /api/regulations/{documentId}/pdf`, `POST /api/regulations/{documentId}/accept` та manager-only `GET /api/regulations/history/employees/{employeeId}` після виконання вимог gate, у межах чинних дозволів. Звірити користувача/роль/документ/версію/час. Перевірити відновлення графіків і swap після accept, архів попередніх PDF та історії.
7. Навчити manager створювати/керувати акаунтами, публікувати графіки, контролювати swap і повідомлення. Swap у застосунку не гарантує юридично правильного робочого часу; рішення й перевірка за роботодавцем.
8. Заповнити акт передачі фактичними функціями, тестером/датою/доказами, навчанням, доступами та незакритими питаннями. Go/no-go ухвалюється за доказами, а не автоматично.

## 7. Шлях працівника та FAQ

Роботодавець визначає законні цілі/підстави для кожної категорії даних, одержувачів, строків, прав і контактів, доставляє власне інформаційне повідомлення та зберігає доказ. Оператор забезпечує доступ до затверджених умов сайту. У gate надходить лише придатний рольово визначений PDF правил застосунку.

Після входу система перевіряє роль і pending. Працівник бачить назву/версію, завантажує PDF, сам ставить порожній checkbox і натискає «Accept and continue». Сервер зберігає персональне підтвердження. Це доказ поданої заяви, а не уважного читання кожного слова, підпису роботодавця чи загальної GDPR-згоди. Якщо pending кілька, потрібно виконати вимоги для всіх; нова обов'язкова версія потребує окремого підтвердження.

**Який PDF підготувати?** Після review — один датований і версійний `Regulamin korzystania z platformy GF3 dla upoważnionych użytkowników`: призначення, хто створює акаунти, особистий доступ, захист PIN/пароля, підтримка/скарги, заборонені дії, роль роботодавця у графіках і swap. Узгодити з публічними умовами. Не завантажувати DRAFT або тихо підміняти старий PDF.

**Що працівник не підтверджує тут?** SaaS/B2B, DPA, TOMs, SLA, рахунки, внутрішні реєстри, трудовий договір або «zgadzam się na przetwarzanie» замість GDPR-інформації.

**Чи потрібен regulamin оператора?** Art. 8 UŚUDE передбачає правила електронної послуги й безоплатне надання до договору у формі, яку можна зберегти/відтворити: функції, технічні умови, заборони, укладення/розірвання, рекламації. Застосовність і фінальний текст перевіряє юрист. Це окремо від правил праці роботодавця. [Джерело: UŚUDE, art. 8](https://eli.gov.pl/api/acts/DU/2024/1513/text.html).

**Чи кожна політика вимагає checkbox?** Ні; спосіб надання та потребу персонального підтвердження визначають за документом і юридичною моделлю. GDPR-інформація не перетворюється на добровільну згоду лише через кнопку. Cookies потребують окремої оцінки реальних механізмів.

**Чи створює GF3 regulamin pracy?** Ні. Це документ роботодавця. За загальними правилами він обов'язковий від 50 працівників; за 20–49 — на вимогу профспілкової організації за умовами закону; можливий добровільно, є винятки щодо колективного договору. Роботодавець ознайомлює працівника перед початком роботи. HR/польський трудовий юрист перевіряє застосовність і спосіб доставки; gate не є автоматично кадровим документообігом. [Джерело: PIP](https://www.pip.gov.pl/dla-pracodawcow/niezbednik-pracodawcy/jak-zatrudnic-pracownika-w-ramach-umowy-o-prace).

## 8. Повсякденна робота, інциденти й вихід

| Подія | Хто діє і що робить | Який доказ лишається у приватному архіві |
|---|---|---|
| Кожний розрахунковий період | Оператор/фінанси звіряють договір, правильний рахунок/документ, оплату; підтримка перевіряє звернення; технічний власник — копії | Документ, платіж, журнал підтримки й backup; автоматичний billing не підтверджений |
| Новий працівник | Роботодавець забезпечує підставу/інформацію; manager створює мінімальний акаунт; користувач підтверджує належний PDF за потреби | Доставка повідомлення, доступ і персональна acceptance-історія |
| Нові правила | Оператор/юрист погоджують текст; system manager публікує новий PDF з датою/версією/hash; попередній зберігають | Review, попередні версії, публікація й нові підтвердження |
| Звільнення | Клієнт відкликає доступ перевіреним способом; відповідальні застосовують погоджену ретенцію | Доказ відкликання, рішення щодо даних/історії; не негайне видалення всього |
| Підозра на витік | Security-власник локалізує, зберігає докази, реєструє й без зайвої затримки повідомляє клієнта-адміністратора через DPA-контакт; далі оновлює факти | Час виявлення/повідомлення, одержувач, дії, докази; конфіденційно |
| Запит людини | Верифікувати заявника, передати роботодавцю-адміністратору, допомогти виконати його рішення за DPA | Запит, передача, інструкція і журнал виконання; не самовільне видалення даних клієнта |
| Припинення підписки | За SaaS/DPA погодити експорт у реально доступному форматі, строк, закриття доступу, повернення/видалення за вибором адміністратора та законними винятками; перевірити копії | Передача експорту, відкликання доступу, протокол видалення/винятків, цикл backup і ретенція договорів/доказів |

72 години стосуються оцінки повідомлення наглядового органу адміністратором за умовами GDPR art. 33, не права процесора чекати 72 години перед повідомленням клієнта. Контакт інцидентів потрібно протестувати до запуску. [GDPR art. 28, 32–34](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng).

Не обіцяй непідтверджений PDF-експорт із UI чи спеціальну міграцію. Визначити строки для акаунтів, графіків/swap, повідомлень, логів, PDF/acceptance, копій і договорів окремо у TOMs; врахувати обов'язкове зберігання та повторне застосування видалень після restore. Періодично перевіряти backup/restore і канали підтримки; частоту та відповідальних погодити, не вигадувати гарантій.

## 9. Go/no-go, невідомі й відповідальні

Для кожного пункту потрібні власник, приватне місце доказу, дата перевірки і статус. Порожнє поле, DRAFT або незакритий ризик означає NO-GO для відповідного етапу. Повний [STOP-SHIP](internal/CHECKLIST_PRZED_STARTEM.md) залишається обов'язковим.

- [ ] Оператор + юрист/бухгалтер: справжня особа, право на SaaS, VAT/ZUS/податки/KSeF, документи й оплата перевірені.
- [ ] Клієнт + юридичний власник: реквізити, представництво, один фінальний SaaS/scope, DPA/TOMs і лише погоджене SLA підписані; delivery evidence збережено.
- [ ] Privacy-власники обох сторін: категорії/підстави, субпроцесори/регіони/transfer, строки, DSAR, повідомлення працівникам затверджені й доставлені.
- [ ] Security/технічний власник: реальний auth/PIN/token, TLS, least privilege, ізоляція, storage/cookies, backup/restore, експорт/видалення перевірені.
- [ ] Оператор + юрист + system manager: публічні тексти/PDF узгоджені, версії/hash/review реальні; scope ролей, pending/428/accept/history та архів перевірені.
- [ ] Оператор + уповноважений клієнт: контакти підтримки/фінансів/інцидентів протестовані, навчання та фактична передача в акті; відкриті питання мають власників, production-блокери не проігноровані.
- [ ] Оператор + клієнт: вихід, експорт/відкликання/повернення/видалення/копії перевірені до production.

Наразі потрібні реальні дані [оператора](OPERATOR_INPUTS.md), затвердження [реєстру review](LEGAL_REVIEW.md), фінальний узгоджений текст старих робочих джерел і public HTML, фактичні хостинг/субпроцесори/retention/restore, підписи та докази інформування. Цей документаційний план не закриває ці людські й серверні блокери.
